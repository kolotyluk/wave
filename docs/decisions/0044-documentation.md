# 0044. Documentation to the standard of the Principles of Operation

- Status: Proposed
- Date: 2026-11-20

## Context

Google Wave had good whitepapers but no single manual that said what Wave was,
and people struggled to understand it.

IBM's *System/360 Principles of Operation* defined an architecture so
precisely that every model from the 360/30 to the /91 implemented it. It
remains a standard for technical documentation. Rust's documentation is a
modern standard: a narrative book, a normative reference, library
documentation with examples tested on every build, and an RFC history.

## Decision

Proposed: Wave has four books, each with one audience.

| Book | For | Contents |
| --- | --- | --- |
| **Wave Rider** | People using Wave | Primer and user manual, taught through worked journeys: a housing letter, a co-op board, a mediation. |
| **Wave Shape** | People building Wave or a door | Architecture, and the **Wave Principles of Operation**: the normative definition of the model, operations, admission, encoding, bounds and views. |
| **Wave Meister** | Experts | Advanced concepts, including the Wave Court. |
| **Wave Reference** | Implementers | rustdoc for the crates, specifications, and the test vectors. |

The decision records remain the design history behind all four.

**Authoring.** Everything is written in Markdown in `docs/`, reviewed like
code. Nobody edits HTML.

**Production.** Wave Rider, Wave Shape and Wave Meister are mdBooks, the tool
the Rust project uses for its own books, with Mermaid for diagrams. Wave
Reference is generated by rustdoc. mdBook can include existing documents,
such as the architecture and the decision records, where they already sit.

**Output.** Builds go to `target/docs/`, which git ignores. Generated HTML is
never committed.

**Publishing.** Continuous integration builds the books on every commit to
`main` and deploys the static files to `docs.wave.ztuph.com`, one path per
book (`/rider/`, `/shape/`, `/meister/`, `/reference/`). The host is a
Cloudflare Pages project of its own, deployed with `wrangler` as `ztuph.com`
already is, so the documentation is served from a CDN with HTTP/3 and IPv6.
The author's portfolio (`kolotyluk.github.io`) links to it. Releases add versioned paths beside
`/latest/`. A PDF of the Principles of Operation can be produced from the same
source.

**Standards.**

1. Every example runs: rustdoc examples are tested, and protocol examples are
   test vectors.
2. Every MUST in the Principles of Operation has a conformance test.
3. Normative text and explanation are never mixed.
4. Nothing is described as existing that does not, unless marked as planned.
5. Missing documentation on public items becomes a build error once code
   exists.

## Consequences

The written specification promised in 0017 is the Principles of Operation.

Normative chapters use RFC 2119 language (MUST, SHOULD, MAY), so they can be
converted to the IETF's format (for example with kramdown-rfc) if the
protocol goes to the IETF.

The documentation follows the HTTP/3 and IPv6 ground floors where its host
supports them, and moves to Canadian hosting with `wave.ztuph.com`.
